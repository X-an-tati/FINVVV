# SecureFin Core Enterprise

Автономный банковский контур и командный центр безопасности на базе **FastAPI**, **SQLite** и **Tailwind CSS**. Проект демонстрирует защиту банковских операций, целостность данных на уровне самой базы данных, контроль клиентских лимитов, идемпотентность переводов и процесс разбора инцидентов.

---

## Пошаговый запуск проекта

### Шаг 1. Перейдите в папку проекта и установите зависимости
Откройте терминал в корневой директории проекта (`FINVVV-main` или `secure_fin`) и выполните установку библиотек:

```bash
pip install -r requirements.txt
```
*(Если устанавливаете вручную без файла: `pip install fastapi uvicorn cryptography pydantic`)*

### Шаг 2. Запустите бэкенд-сервер (FastAPI + Uvicorn)
В этом же терминале запустите сервер:

```bash
uvicorn main:app --reload
```

**Что происходит при запуске:**
1. FastAPI инициализирует приложение и подключает CORS-middleware.
2. Срабатывает событие старта (`@app.on_event("startup")`), которое вызывает `init_db()` из `database.py`.
3. В папке проекта автоматически создаётся файл базы данных `securefin_core.db` со всеми таблицами, ограничениями `CHECK`, триггерами и представлением `v_transactions_overview`.
4. В терминале появляется сообщение:
   `Uvicorn running on http://127.0.0.1:8000`

* **Проверка работы API:** откройте в браузере `http://127.0.0.1:8000/` (должен вернуться JSON со статусом `ARMED & OPERATIONAL`) или `http://127.0.0.1:8000/docs` (интерактивная документация Swagger UI).

> **Примечание при обновлении кода:** если вы меняли структуру таблиц в `database.py` и при запросах видите ошибку `no such table` или `no such column`, остановите сервер (`Ctrl + C`), удалите старый файл `securefin_core.db` и снова выполните `uvicorn main:app --reload`.

### Шаг 3. Откройте веб-интерфейс (`index.html`)
* Откройте файл `index.html` в браузере (двойным кликом по файлу или через локальный сервер / Live Server, например на `http://localhost:3000`).
* Интерфейс автоматически обратится к `http://127.0.0.1:8000` и загрузит текущую статистику, журнал инцидентов и реестр аудита.

### Шаг 4. (Опционально) Запуск демо-скрипта
Для автоматического прогона тестовых сценариев при работающем сервере откройте второй терминал в папке проекта и выполните:

```bash
python demo.py
```

## Как проект работает изнутри (от А до Я)

### 1. Архитектура и роль каждого файла
* **`database.py` — уровень хранения и защиты данных (SQLite)**
  * Создаёт 7 таблиц: `users` (клиенты и роли), `accounts` (счета с зашифрованным балансом и дневным лимитом), `transactions` (переводы с ключом идемпотентности), `audit_logs` (журнал с хеш-цепочкой), `account_history` (история изменений балансов), `blocked_ips` (чёрный список IP) и `incidents` (карточки инцидентов).
  * Защищает данные на уровне СУБД через `CHECK` и `NOT NULL` (нельзя записать сумму `<= 0`, неверный статус или отрицательный лимит даже при прямом SQL-запросе в обход API).
  * Создаёт SQL-триггеры (`trigger_tamper_protection` и `trigger_account_history`), которые автоматически фиксируют любое обновление строки в таблице `accounts`.
  * Создаёт представление (`VIEW`) `v_transactions_overview`, объединяющее ID транзакций, логины отправителя и получателя, суммы и статусы.
* **`security.py` — криптографический модуль**
  * `hash_password()` — хеширует пароли пользователей перед записью в БД.
  * `encrypt_data()` / `decrypt_data()` — шифрует и расшифровывает балансы счетов, чтобы в таблице `accounts` хранился шифротекст, а не открытые суммы.
* **`main.py` — бизнес-логика, безопасность и API**
  * Принимает HTTP-запросы от фронтенда, проверяет режим изоляции (`SYSTEM_LOCKDOWN`), права доступа по заголовку `X-Role` (`SECURITY_OFFICER`, `OPERATOR`, `AUDITOR`), ведёт антифрод-скоринг и формирует криптографическую цепочку логов.
* **`index.html` — командный центр**
  * Отправляет запросы через `fetch` к FastAPI, отображает KPI-метрики, позволяет управлять ролями, переводить средства, симулировать атаки и выгружать отчёт.

---

### 2. Жизненный цикл перевода (`POST /transfer`)

Когда пользователь нажимает **«Выполнить перевод»**, запрос проходит 6 последовательных этапов:

1. **Проверка Kill Switch (`DEFCON 1`):** если офицер безопасности активировал режим изоляции, сервер сразу отклоняет запрос (`HTTP 403`).
2. **Проверка идемпотентности (`idempotency_key`):** если запрос с таким же ключом уже был успешно обработан ранее, списание не дублируется — сервер возвращает сохранённый результат (`IDEMPOTENT_REPLAY`).
3. **Проверка IP и валидация счетов:** проверяется, не находится ли IP в таблице `blocked_ips`, проверяются существование счетов отправителя и получателя, положительность суммы и расшифровываются текущие балансы.
4. **Контроль дневного лимита (`daily_limit`):** сервер суммирует успешные переводы отправителя за текущие сутки и блокирует операцию, если новая сумма превышает установленный лимит счёта.
5. **Двухфакторная проверка (2FA) и Anti-Fraud:**
   * при переводе свыше `100 000 KZT` генерируется и проверяется одноразовый код (`OTP`);
   * антифрод-движок начисляет баллы риска (`risk_score` от `0` до `100`) за нехватку средств, аномально крупную сумму (`> 500 000 KZT`), высокую частоту операций (`>= 3` за минуту) или признаки подозрительной сети (`RED TEAM ATTACK`).
6. **Запись результата в БД и хеш-цепочку:**
   * **Если операция заблокирована (`risk_score >= 80` или нехватка средств):** транзакция сохраняется со статусом `BLOCKED`, IP заносится в `blocked_ips`, в таблице `incidents` создаётся открытый инцидент (`OPEN`), а в `audit_logs` пишется событие блокировки.
   * **Если операция одобрена:** балансы отправителя и получателя пересчитываются, шифруются и обновляются в `accounts` (автоматически срабатывают триггеры SQLite и пишется `account_history`), транзакция сохраняется со статусом `SUCCESS`, а в `audit_logs` добавляется новая запись.

---

### 3. Как работает защита от подделки логов и отчётность
* **Хеш-цепочка (`audit_logs`):** каждая новая запись берёт `record_hash` предыдущей строки (`prev_hash`) и вычисляет свой `SHA-256` от связки `prev_hash | user_id | action | details`. При нажатии **«Цепь БД & VIEW»** (`GET /db-chain-check`) сервер пересчитывает всю цепочку с первой записи и показывает, не были ли логи изменены вручную.
* **Подписанный отчёт (`GET /export-report`):** собирает срезы из `transactions`, `audit_logs`, `blocked_ips` и `incidents`, вычисляет общий криптографический дайджест `SHA-256` и позволяет скачать готовый JSON-файл для проверки и комплаенса.

## Структура репозитория

```text
FINVVV-main/
├── database.py       # Инициализация SQLite, CHECK-ограничения, триггеры, VIEW
├── main.py           # REST API (FastAPI), Anti-Fraud, RBAC, хеш-цепочка, отчёты
├── security.py       # Хеширование паролей и шифрование/расшифровка балансов
├── demo.py           # Скрипт демонстрации и проверки сценариев
├── index.html        # Веб-интерфейс командного центра (Tailwind CSS + JS)
├── requirements.txt  # Зависимости Python
├── .gitignore        # Исключение локальной БД (*.db), кэша и временных файлов
└── README.md         # Документация проекта
```
